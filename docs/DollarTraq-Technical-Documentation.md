## 1. Product Overview

DollarTraq is a freight-brokerage risk and onboarding platform. It answers one question for a freight broker: **"Is it safe to give this carrier a load and my money?"** — and then carries the broker through onboarding that carrier, paying them and tracking the relationship.

The platform serves **three distinct audiences**, each with its own authentication, its own permission matrix and its own set of screens:

| Audience | Who they are | How they get in | What they can do |
|---|---|---|---|
| **Broker staff** | Employees of a brokerage that subscribes to DollarTraq | Sign up / are invited by a colleague; email + password + optional OTP | Search carriers, read risk scores, onboard carriers, book loads, manage the company |
| **Carrier (onboarding)** | A trucking company that has just been invited. **Not yet a user of the system.** | A signed 64-character invitation link emailed to their FMCSA-registered address | Complete a four-step onboarding wizard: verify identity, connect payouts, answer questions, sign the agreement |
| **Carrier (portal)** | The same trucking company, after onboarding completes | Credentials generated by the platform at the end of onboarding; email + password + OTP | See their own profile and score, their assigned loads, their documents, and manage their own staff |

The two carrier states are deliberately separate. During onboarding the carrier has **no account** — authorisation is carried entirely by the invitation token in the request body. The account only exists once onboarding has produced a verified identity and a signed agreement.

### 1.1 The core value proposition

1. **Carrier intelligence.** Every US carrier's FMCSA census, inspection, crash, violation and insurance history is queryable, assembled into a profile and scored.
2. **Trust Score.** A weighted, configurable score built from authority, insurance, activity and network signals, with a pillar-level breakdown so the broker can see *why*.
3. **Risk gates.** Scores translate into gates — soft gates a manager can override, knockout gates that require dual control — so risk decisions are policy, not opinion.
4. **Compliant onboarding.** Email verification → SMS OTP → government-ID liveness check → payout account → questionnaire → e-signature, with every step timestamped and IP-logged.
5. **A carrier-facing portal.** Carriers see their own record instead of emailing the broker for it.

### 2.2 Two databases, on purpose

| Connection | Purpose | Access mode | Notes |
|---|---|---|---|
| `mysql` (default) | Application data — users, companies, roles, shipments, onboarding requests, documents, audit trails | Read/write | Migrations apply here only |
| `external_db` | The carrier intelligence database (FMCSA census, inspections, crashes, violations, insurance) hosted separately | **Read-only from the application** | 5-second PDO timeout, optional TLS CA (`EXTERNAL_DB_SSL_CA`). A `CheckExternalDb` artisan command probes reachability. |

Keeping the carrier feed on a separate connection means a slow or unavailable intelligence database degrades carrier search — it does not take down authentication, onboarding or load management.

### 2.3 Application layering

```
Route  ──▶  FormRequest      (validation, authorisation)
       ──▶  Controller       (HTTP shape, envelope, status codes)
       ──▶  Service          (business rules — the substance)
       ──▶  Model / Resource (persistence, response shaping)
```

Business logic lives in `app/Services` (24 service classes), not in controllers. Every API response is normalised through `BaseController` into one envelope, and permission failures are rendered as a consistent JSON 403 by a global exception handler.

## 3. Feature Catalogue — Broker Portal

### 3.1 Carrier search & directory

* Full-text and filtered search across the carrier database (`GET /v1/carrier/search`).
* Results are transformed into a consistent card shape; filters are applied server-side.
* Every search is written to **search history** (`search_histories`), scoped to the company, along with the DT Score at the time of search — so a broker can prove what they saw and when.

### 3.2 Carrier profile & intelligence

| Endpoint | What it returns |
|---|---|
| `GET /v1/carrier/{dot}/trust-score` | The Trust Score and its pillar breakdown |
| `GET /v1/carriers/{dot}/risk` | Full risk assessment: authority flags, insurance flags, activity flags, network flags, benchmarks |
| `GET /v1/carriers/{dot}/associations` | Related entities — shared addresses, officers, phone numbers |
| `GET /v1/carrier/{dot}/vin-association` | Equipment/VIN overlap with other carriers (a classic chameleon-carrier signal) |
| `POST /v1/carrier/detail/{rowid}` | The full assembled profile |

The assembled profile includes: authority age, DOT age, ownership profile, cargo carried, preferred lanes, insurance history, email-domain and web-presence signals, and recent inspections, crashes, crash details and violation details.

**Performance controls.** Profiles are cached (`CARRIER_PROFILE_CACHE_TTL`, default 900s) because FMCSA data changes at most daily. Child collections are capped (`CARRIER_RECENT_LIMIT`, default 25 rows) while totals are always reported in full under `computed`. An optional live FMCSA API snapshot is cached separately for 24 hours with an 8-second timeout, because the upstream service is slow and frequently unavailable.

### 3.3 Trust Score configuration

* `POST /v1/scoring-weights` — an Owner/Admin can change the weighting of the scoring pillars (`edit-scoring-config`).
* `GET /v1/scoring-weights/active` and `/templates` — the currently active weights and the packaged starting templates.
* Weights are **company-scoped**: two brokerages on the platform can score the same carrier differently according to their own risk appetite.

### 3.4 Shortlists, reports & incident history

* **Shortlist** (`/v1/shortlist`) — a company-scoped saved list of carriers.
* **Carrier reports** (`/v1/carrier-reports`) — a broker can file a report against a carrier (fraud, non-performance, double-brokering). Reports are emailed via `CarrierReportMail`.
* **Incidents** (`GET /v1/carrier-reports/incidents`) — the aggregated incident history a broker sees on a carrier profile.

### 3.5 Loads & shipments

| Capability | Endpoint | Permission |
|---|---|---|
| List loads | `GET /v1/shipments` | `view-loads-tracking` |
| Load detail | `GET /v1/shipments/{uuid}` | `view-loads-tracking` |
| Create a load | `POST /v1/shipments` | `book-assign-loads` |
| Add stops | `POST /v1/shipments/{uuid}/stops` | `book-assign-loads` |
| Load templates | `GET /v1/shipment-templates`, `/{tracking_number}` | `view-loads-tracking` |
| PRO-number collision check | `POST /v1/check-pro-number` | authenticated |

Shipments carry generated shipment numbers, multi-stop itineraries (`shipment_stops`) and tracking-update fields for ELD integration.

### 3.6 OCR

`POST /v1/ocr-data` extracts structured data from uploaded documents (e.g. certificates of insurance) — backed by `coi_document_extractions`, so an extraction is stored and auditable rather than discarded.

### 3.7 Broker agreement documents

The legal agreement a carrier signs is uploaded and versioned by the broker, stored on **S3** (`config/agreements.php`).

| Action | Endpoint | Permission |
|---|---|---|
| List / show | `GET /v1/agreement-documents`, `/{uuid}` | authenticated |
| Create / update | `POST /v1/agreement-documents`, `POST /{uuid}` | `edit-carrier-agreements` |
| Activate / deactivate | `PATCH /{uuid}/status` | `edit-carrier-agreements` |
| Delete | `DELETE /{uuid}` | `edit-carrier-agreements` |

### 3.8 Email template editor

Every outbound mail can be customised per company, with a documented placeholder vocabulary served to the editor so users never have to guess variable names.

| Template type | Sent when |
|---|---|
| `invitation` | A teammate is invited to the company |
| `login_otp` | A user signs in with two-factor enabled |
| `password_reset` | A user requests a password reset |
| `carrier_agreement` | The broker agreement is sent to a carrier |
| `carrier_connect` | A broker clicks **Connect** on a carrier profile |
| `carrier_account` | Onboarding completes and portal credentials are issued |
| `custom` | Any other mail the team sends |

Templates support live preview with sample values (`POST /v1/email-templates/{uuid}/preview`), a default-per-type flag, and **HTML sanitisation on save** (`EmailTemplateService::sanitize`) so a rich-text editor cannot become a stored-XSS vector.

### 3.9 Carrier questionnaire builder

`/v1/carrier-questions` (CRUD) lets a brokerage define the questions every carrier must answer during onboarding. Answers land in `carrier_connect_answers` against the specific onboarding request.

### 3.10 Company & team management

* `GET/PUT /v1/company` — company profile, editable with `edit-company-profile-billing`.
* `GET /v1/users`, `GET /v1/roles`, `POST /v1/invitations` — team roster, assignable roles and invitations, gated behind `manage-users-basic` or `manage-users-all`.
* Invitations carry a **temporary password**; the invited user is forced through a password change by the `EnsurePasswordChanged` middleware before any other endpoint will answer.

## 4. Feature Catalogue — Carrier Connect (Onboarding)

This is the most security-sensitive flow in the product: it turns a row in a public government dataset into a paid, contracted counterparty.

### 4.1 The invitation

A broker with `send-invitation-approved-carriers` clicks **Connect** on a carrier profile. The API:

1. Creates a `carrier_connect_requests` row, scoped to the **broker company** — not the individual sender — so any teammate can see, continue or resend an onboarding a colleague started.
2. Generates a 64-character random token with a configurable lifetime (`CARRIER_CONNECT_LIFETIME_HOURS`, default **72 hours**).
3. Emails the link **only to the carrier's FMCSA-registered address**, using the company's `carrier_connect` template.

**Alternate-email consent.** If the carrier wants onboarding to run through a different inbox, the platform will not simply accept it. An approval mail goes to the FMCSA-registered address; opening that link (`/carrier/connect/approve-email/{token}`, rate-limited 30/min) is the carrier consenting, and is the **only** thing that releases the invitation to the alternate address. This is tracked in dedicated columns (`pending_email_requested_at` and companions).

**Development safety.** Because carrier contact details are real data from a public feed, `CARRIER_CONNECT_TEST_EMAIL` / `CARRIER_CONNECT_TEST_PHONE` redirect all mail and SMS in non-production environments. Both must be empty in production.

### 4.2 The wizard

| # | Step | Endpoint | What actually happens |
|---|---|---|---|
| 0 | Open the link | `GET /carrier/connect/{token}` (web, 30/min) | Landing here proves mailbox control → status becomes `email_verified` |
| 1 | Phone OTP | `POST /v1/carrier-connect/otp/send` (10/min)<br>`/otp/verify` (15/min) | 6-digit code by SMS via Telnyx. Code is **hashed** at rest, expires in 15 min (`CARRIER_CONNECT_OTP_MINUTES`), 3 attempts max (`CARRIER_CONNECT_OTP_ATTEMPTS`) → `mobile_verified` |
| 2 | Identity verification | `/identity/start`, `/identity/verify`, `/identity/webhook` | A Didit v3 verification session — government ID + liveness. Didit calls the webhook server-to-server → `id_verified` |
| 3 | Payout account | `/stripe/connect`, `/stripe/verify` | A Stripe Express account is created and onboarded → `bank_verified` |
| 3b | Factoring (alternative) | `/factoring` | Carriers paid through a factoring company upload the factoring notice (PDF only) instead of connecting Stripe |
| 4 | Questionnaire | `/questions`, `/answers` | The broker's configured questions and the carrier's answers → `questionnaire_done` |
| 5 | Documents | `/documents`, `/documents/{type}/remove` | W-9 and Certificate of Insurance. PDF/JPG/PNG, 10 MB cap |
| 6 | Agreement & e-signature | `GET /agreement/{token}`, `POST /esign` | The broker's agreement is **streamed by the API** rather than linked to S3 (the bucket sends no CORS headers), then signed → `completed` |
| — | Skip a step | `/skip` | Steps the broker has marked optional are recorded as explicitly skipped (`step_skips`), never silently absent |

Every step is authorised by the invitation token in the request body — there is no session and no account. The whole wizard is rate-limited to 60 requests/minute, which is generous for a human working through six steps and tight enough to stop enumeration.

### 4.3 What is recorded

* **Onboarding IP** (`onboarding_ip`) — where the carrier onboarded from.
* **Prefill tracking** (`prefilled_at`) — which fields the platform pre-populated from FMCSA versus which the carrier typed. This matters: a broker should know whether the carrier confirmed a detail or the system guessed it.
* **Status history** through the seven statuses: `new → email_verified → mobile_verified → id_verified → bank_verified → questionnaire_done → completed`.
* **Derived stage.** Expiry and a failed ID check are folded into the raw status by the API resource layer, and the list summary is counted the same way, so the badge on a row and the count in the header can never disagree.

The token and OTP are in the model's `$hidden` array — they cannot leak through an API response even by accident.

### 4.4 Account provisioning

When onboarding completes, `CarrierAccountService::provisionFor()`:

1. Creates a `carrier_companies` record and a `carrier_users` owner account.
2. Generates a temporary password (hashed with the application hasher; never stored in clear).
3. Seats the first person as **Carrier Owner / Admin** — the person who signed and gets paid.
4. Emails the credentials and the portal URL using the `carrier_account` template.
5. Forces a password change on first sign-in via `EnsurePasswordChanged`.

### 4.5 Broker-side visibility

* `GET /v1/carrier-connect` — every onboarding the company has running, searchable by legal name, DOT or email, with the derived stage.
* **Login-location cross-check.** The list resolves each carrier's most recent *successful* portal sign-in IP in a single query, so a broker can compare where the carrier onboarded from with where they actually sign in — a cheap, effective fraud signal. Failed attempts are excluded, because a failed attempt says nothing about where the real carrier is.
* `GET /v1/carrier-connect/{uuid}/files/{type}` — download what the carrier submitted.

## 5. Feature Catalogue — Carrier Portal

A separate application, a separate model (`CarrierUser`), a separate Spatie guard (`carrier`). `EnsureCarrierUser` keeps a broker token out of the portal; `EnsureBrokerUser` keeps a carrier token out of the broker API. Even a role-name collision could not cross the boundary.

### 5.1 Authentication

| Endpoint | Purpose |
|---|---|
| `POST /v1/carrier-portal/login` | Credentials; returns a token directly if the device is trusted, otherwise an OTP challenge |
| `POST /v1/carrier-portal/verify-login-otp` | 6-digit emailed code — 10-minute TTL, 5 attempts |
| `POST /v1/carrier-portal/forgot-password` → `verify-forgot-password-otp` → `reset-password` | Three-step reset: OTP (10 min, 5 attempts) then a single-use 64-char reset token (15 min) |
| `GET /me`, `POST /logout`, `POST /change-password` | Session management |

All of the above are rate-limited to **10 requests/minute**.

### 5.2 Trusted devices & sign-in trail

* `GET /devices` — remembered devices; a trusted device suppresses the OTP for **30 days**.
* `POST /devices/forget` — revoke one.
* `GET /login-history` — every sign-in attempt with outcome and IP (`carrier_login_attempts`), visible to the carrier themselves.

### 5.3 Profile

`GET /carrier-portal/profile` returns the carrier's company card, FMCSA snapshot, Trust Score and an **onboarding completeness** breakdown.

Deliberately, **the only thing the profile screen can write is the photo** (`POST`/`DELETE /profile/photo`). Legal name, DOT/MC, authority and company details are FMCSA and onboarding data — read-only for every seat, owner included. A carrier cannot edit their way to a better record.

### 5.4 Brokers, loads and documents

| Endpoint | Permission | Notes |
|---|---|---|
| `GET /brokers` | `view-own-carrier-profile` | Which brokers this carrier has onboarded with |
| `GET /loads`, `GET /loads/{uuid}` | `view-assigned-loads` | Read-only: the shipment is the broker's record |
| `GET /documents` | `view-own-carrier-profile` | The paperwork handed over during onboarding |
| `GET /documents/{connectionUuid}/{type}/download` | `view-own-carrier-profile` | **Streamed, never linked** — files sit on the private disk, and the allowed `{type}` values are whitelisted at the route level |

### 5.5 Carrier team management

* `GET /users` — everyone in the account can see who else is in it.
* `GET /roles`, `POST /users/invite`, `PUT /users/{uuid}` — gated behind `manage-carrier-users`, which belongs to the **Carrier Owner / Admin seat only**. User management is one of the sensitive writes that is deliberately not delegable.
* Invitations lapse after 7 days (`invitation_lifetime_days`).

## 6. Feature Catalogue — Platform & Administration

* **Multi-tenancy.** Every business record carries a `company_id` and every query is scoped to the authenticated user's company. Shortlists, search history, scoring weights, agreements, email templates, questionnaires and onboarding requests are all company-scoped.
* **Config-as-source-of-truth RBAC.** `config/rbac.php` and `config/carrier_rbac.php` are the single definition of every role and permission; seeders sync the database from them. A permission change is a reviewed code change, not a database edit.
* **Consistent API envelope.** One response shape and one error shape across the whole surface, including a global handler that renders Spatie authorisation failures as `403` with the list of required permissions.
* **DT Pay (payments).** The permission matrix defines the full DT Pay authority model — create & fund, capped release, unlimited release, refund/cancel — and the Senior Agent seat carries a **$5,000** per-payment conditional-release cap. ⚠ **Status:** legacy DT Pay controllers exist in `app/Http/Controllers/DtPay` but are **not currently exposed in the v1 API**; the feature is defined in policy ahead of its API implementation.

## 10. Authentication & Session Management

### 10.1 Two independent identity systems

| | Broker staff | Carrier portal |
|---|---|---|
| Model | `User` | `CarrierUser` |
| Guard | `web` (session) / Sanctum for API | `carrier` (Sanctum) |
| Token name | `broker-api` | `carrier_user_api_token` |
| Middleware wall | `EnsureBrokerUser` | `EnsureCarrierUser` |
| Permission source | `config/rbac.php` | `config/carrier_rbac.php` |

A token issued to one audience is rejected by the other's endpoints at the middleware layer, before any controller runs.

### 10.2 Sign-in

1. **Credentials.** Email + password, verified against a hash. Passwords are stored with Laravel's default hasher (**bcrypt**) via `Hash::make()` — never in clear text, never reversibly encrypted, anywhere in the codebase.
2. **Two-factor (OTP).** If two-factor is enabled for the user — and mandatory for carrier portal users on an untrusted device — a **6-digit code generated with `random_int()`** (a cryptographically secure source, not `rand()`) is emailed. The code is **hashed with `Hash::make()` before storage**: a database compromise does not reveal live OTPs.
3. **Token issue.** On success, a Sanctum personal access token is issued and returned to the client.

### 10.3 OTP and token parameters

| Control | Broker | Carrier portal | Carrier onboarding |
|---|---|---|---|
| OTP length | 6 digits | 6 digits | 6 digits |
| OTP lifetime | 10 minutes | 10 minutes | 15 min (configurable) |
| Max attempts | 5 | 5 | 3 (configurable) |
| Delivery | Email | Email | **SMS** (Telnyx) |
| Stored as | bcrypt hash | bcrypt hash | bcrypt hash |
| Trusted device | 1 year | **30 days** | n/a |
| Password reset token | 64 chars, 15 min, single use | 64 chars, 15 min, single use | n/a |

### 10.4 Forced password change

Any account created with a system-generated temporary password — an invited broker teammate, an invited carrier user, a newly provisioned carrier owner — is blocked by `EnsurePasswordChanged` from every authenticated endpoint until the password is changed.

### 10.5 Session timeout

| Setting | Value | Where |
|---|---|---|
| Web session lifetime | 120 minutes | `SESSION_LIFETIME` |
| Session driver | database | `SESSION_DRIVER` |
| Cookie `HttpOnly` | true | `SESSION_HTTP_ONLY` |
| Cookie `SameSite` | lax | `SESSION_SAME_SITE` |
| Cookie `Secure` | environment-driven — **must be `true` in production** | `SESSION_SECURE_COOKIE` |
| API token expiry | **currently unlimited** (`sanctum.expiration = null`) | see §21 |

### 10.6 Rate limiting

Applied per route, tuned to the cost and risk of each action:

| Route group | Limit |
|---|---|
| Broker forgot/reset password | 10 / min |
| Carrier portal login & password reset | 10 / min |
| Carrier onboarding wizard | 60 / min |
| Agreement PDF stream | 60 / min |
| **SMS OTP send** (costs money) | **10 / min** |
| OTP verify | 15 / min |
| Invitation / approval links (web) | 30 / min |

## 11. Authorisation — Role-Based Access Control

Authorisation is enforced at the route layer with `PermissionMiddleware`, so an endpoint cannot be reached at all without the permission, and a missing permission never depends on a controller remembering to check.

### 11.1 Broker roles

| Role | Level | Risk authority | Payment release cap | Summary |
|---|---|---|---|---|
| **Viewer** | 10 | none | — | Read-only carriers, scores and loads. No PII, no actions. |
| **Agent** | 20 | none | — | Invite approved carriers, book loads, initiate payments. Partial carrier PII only. |
| **Senior Agent** | 30 | can *request* exceptions | **$5,000** | Agent + full sensitive data + capped payment release. |
| **Compliance Manager** | 40 | override soft gates | unlimited | Approves and clears flags, confidence caps and below-band onboarding. Manages agreements, templates and junior users. |
| **Owner / Admin** | 50 | soft **and** knockout gates | unlimited | Everything: scoring config, billing, role management, hard-gate overrides (dual control). |

### 11.2 Broker permission groups

| Group | Permissions |
|---|---|
| **Carriers** | view directory & profiles · view Trust Score + pillars · view partial sensitive data (legal name, MC/DOT, contact) · view **full** sensitive data (EIN/SSN/bank/W-9) · rate & note · invite approved carriers · request invite to flagged carriers · invite flagged carriers |
| **Loads** | view loads & ELD tracking · book / assign loads |
| **Payments (DT Pay)** | create & fund · release conditional payment (capped) · release conditional payment (unlimited) · refund / cancel |
| **Risk** | request/clear manual-review flag · request/lift data-confidence cap (1 tier / full) · request/apply soft-gate override · override knockout gate (dual control) |
| **Administration** | edit carrier agreements, questions & templates · manage users (basic / all) · edit scoring config · edit company profile & billing · manage API keys & integrations |

**Two design decisions worth stating explicitly:**

1. **Request vs. approve are different permissions.** A `*-request` permission means "can flag the exception"; the approval always belongs to a Compliance Manager or above. One person cannot both raise and clear a risk exception.
2. **Override authority is separable from seat.** `can_override_soft` and `can_override_gate` live on the *user* row as well as the role, so risk authority can be granted or withdrawn from an individual without changing their job title in the system.

### 11.3 Role assignment rules

| A holder of… | May assign |
|---|---|
| Owner / Admin | Viewer, Agent, Senior Agent, Compliance Manager, Owner/Admin |
| Compliance Manager | Viewer, Agent, Senior Agent |
| Senior Agent, Agent, Viewer | *nothing* |

Creating another Owner/Admin or Compliance Manager is reserved for an Owner/Admin — a manager cannot promote their way upward.

### 11.4 Carrier portal roles

| Role | Level | Summary |
|---|---|---|
| **Driver / Viewer** | 10 | Own status, assigned loads, tracking consent. No sensitive writes. |
| **Carrier Staff** | 20 | Onboarding tasks, document upload, load management, contact info, payment visibility. No sensitive writes. |
| **Carrier Owner / Admin** | 30 | Everything staff can do, **plus** banking & payout, W-9 / legal identity, KYC, signing agreements, and managing carrier users. |

**The sensitive group.** Payout banking, legal identity, KYC and agreement signing sit in exactly one seat — the Carrier Owner/Admin. This is the point of the matrix: a trucking company can delegate day-to-day dispatch work to staff **without handing over payout control**. Only the owner may seat anyone, including another owner.

### 12.2 API conventions

* **Base path:** `/api/v1`
* **Health check:** `GET /api/v1/health` and the framework probe at `/up`
* **Auth header:** `Authorization: Bearer <sanctum-token>`
* **Identifiers:** UUIDs in URLs for user-facing records — sequential integer IDs are never exposed
* **Response envelope:** `{ status, message, data }`; errors return `{ status: false, message, errors }`
* **403 shape:** authorisation failures include `errors.required_permissions` so the frontend can explain *what* was missing
* **JSON is forced** for every `api/*` route by the global exception handler — an error never returns an HTML error page to an API client

### 12.3 Public (unauthenticated) endpoints

Only these are reachable without a token. Everything else requires authentication **and** a permission:

`/v1/health` · `/v1/signup` · `/v1/login` · `/v1/verify-login-otp` · `/v1/invitations/accept` · `/v1/forgot-password` · `/v1/verify-forgot-password-otp` · `/v1/reset-password` · `/v1/getCarrier` · all `/v1/carrier-connect/*` wizard routes (authorised by invitation token) · `/v1/carrier-portal/login` and password-reset routes · the two web invitation links.

## 14. Security Controls

### 14.1 Transport and network

| Control | Implementation |
|---|---|
| HTTPS everywhere | TLS terminated at the web tier; HTTP redirected to HTTPS ⚠ TO CONFIRM certificate provider and renewal |
| Security groups | EC2 exposes only 80/443 publicly; SSH restricted to known addresses ⚠ TO CONFIRM |
| Database exposure | Application database is not publicly reachable ⚠ TO CONFIRM |
| Carrier database link | Separate connection, 5-second timeout, optional TLS CA (`EXTERNAL_DB_SSL_CA`) |

### 14.2 Identity and access

| Control | Implementation |
|---|---|
| Password hashing | Laravel `Hash::make()` (bcrypt). No plaintext or reversible storage anywhere in the codebase. |
| OTP hashing | OTPs are hashed before storage, in all four OTP flows |
| Secure randomness | `random_int()` for OTPs, `Str::random(64)` for invitation and reset tokens |
| Multi-factor | Email OTP for both portals; SMS OTP during onboarding; trusted-device suppression with an explicit expiry |
| Brute-force limits | Per-record attempt counters (3–5) **plus** per-route rate limits |
| Forced password rotation | `EnsurePasswordChanged` on every temporary-password account |
| Least privilege | 28 broker permissions and 13 carrier permissions, enforced at the route |
| Audience isolation | `EnsureBrokerUser` / `EnsureCarrierUser`, separate models, separate Spatie guards |
| Separation of duties | Request-vs-approve permission split; dual control on knockout-gate override; non-delegable carrier sensitive writes |
| Sign-in auditing | `carrier_login_attempts` records outcome and IP for every attempt; `login_devices` for broker devices |

### 14.3 Input handling

| Control | Implementation |
|---|---|
| Input validation | Dedicated `FormRequest` classes per endpoint, with authorisation and human-readable messages |
| SQL injection | Eloquent ORM and the query builder throughout — parameter-bound. No string-concatenated SQL. MySQL strict mode on. |
| XSS | API returns JSON, not HTML. Rich-text email templates are **sanitised on save** (`EmailTemplateService::sanitize`). |
| CSRF | Stateless bearer-token API — the standard CSRF vector does not apply. Laravel's CSRF middleware protects the web routes. |
| File upload | Whitelisted MIME types (`pdf,jpg,jpeg,png`; factoring notices PDF-only), **10 MB cap**, whitelisted document types, generated storage filenames |
| Route-level whitelisting | `whereIn('type', …)` on document downloads and `where('dot', '[0-9]+')` on numeric routes — invalid values 404 before reaching a controller |
| Mass assignment | Explicit `$fillable` on every model |
| Sensitive field leakage | `$hidden` on models — the invitation token and OTP can never appear in a response |

### 14.4 Data protection

| Control | Implementation |
|---|---|
| Storage isolation | Carrier documents live on the **private** disk. They are streamed through an authorised endpoint, never linked directly. |
| S3 permissions | Buckets are private; no public-read objects; access via IAM credentials scoped to the application ⚠ TO CONFIRM bucket policy and Block Public Access |
| CORS-safe delivery | The agreement PDF is proxied through the API rather than linked to S3 |
| Encryption in transit | TLS to the API, to S3, to every third party |
| Encryption at rest | ⚠ TO CONFIRM RDS/EBS encryption and S3 default encryption (SSE-S3 or SSE-KMS) |
| Secrets | `.env`, outside version control. `APP_KEY` per environment. ⚠ Recommend migrating to AWS Secrets Manager or SSM Parameter Store (see §21) |
| Tenant isolation | Company scoping on every business query |
| Data minimisation | Banking and identity documents are held by Stripe and Didit, not DollarTraq |

## 16. Backup & Recovery

⚠ **This section describes the intended posture. Every line must be confirmed against the actual AWS configuration before this document is used as evidence.**

| Item | Policy |
|---|---|
| **Database backup schedule** | Automated daily snapshot, retained 7–30 days ⚠ TO CONFIRM mechanism (RDS automated backups vs. `mysqldump` cron) and retention |
| **Point-in-time recovery** | ⚠ TO CONFIRM whether enabled |
| **S3 backup** | S3 is durable by design (11 nines). ⚠ TO CONFIRM whether **versioning** is enabled — versioning, not durability, is what protects against accidental deletion and ransomware. |
| **Backup encryption** | ⚠ TO CONFIRM |
| **Restore testing** | ⚠ **Recommended and currently unverified:** restore the latest backup into a scratch environment at least quarterly and record the result. An untested backup is not a backup. |
| **RPO (recovery point objective)** | Target: ≤ 24 hours ⚠ TO CONFIRM |
| **RTO (recovery time objective)** | Target: ≤ 4 hours ⚠ TO CONFIRM |

**Recovery procedure (outline).**

1. Declare the incident and notify the access holders (§20).
2. Put the application into maintenance mode (`php artisan down`).
3. Provision a replacement instance from the latest AMI / deployment, or restore the existing one.
4. Restore the database from the most recent verified snapshot.
5. Verify `APP_KEY` matches the restored data — **a mismatched `APP_KEY` makes encrypted columns unreadable.**
6. Run `php artisan migrate --force` and clear caches.
7. Confirm `GET /api/v1/health`, a sign-in, and one carrier profile read.
8. Bring the application up and record a post-incident timeline.

**Disaster recovery.** ⚠ TO CONFIRM whether backups are replicated to a second AWS region. Single-region backups do not survive a regional failure.

## 17. Incident Management

### 17.1 Severity levels

| Severity | Definition | Response target | Who is engaged |
|---|---|---|---|
| **S1 — Critical** | Platform down, data loss, confirmed security breach, payments failing | Immediate | All access holders + client |
| **S2 — High** | A major feature broken for all users; no data loss | Same business day | Development team |
| **S3 — Medium** | Feature degraded, workaround exists | Next working day | Assigned developer |
| **S4 — Low** | Cosmetic or minor | Next release | Backlog |

### 17.2 Bug reporting

1. Reported through the agreed channel (GitHub Issues / client channel) ⚠ TO CONFIRM which is authoritative.
2. Each report must carry: environment, steps to reproduce, expected vs. actual, user role, timestamp, screenshots.
3. Triaged to a severity and an owner within one working day.
4. Fixed on a branch, reviewed, and shipped through the normal lifecycle — or, for S1/S2, through the hotfix path.

### 17.3 Security incident reporting

1. **Report immediately** to the production access holders — do not open a public issue for a suspected vulnerability.
2. **Contain first:** revoke affected Sanctum tokens, rotate the exposed credential, block the source if applicable.
3. **Preserve evidence:** copy the relevant logs *before* restarting or redeploying anything.
4. **Assess scope:** which records, which tenants, which individuals' personal data.
5. **Notify:** the client, and any affected carriers where personal data is involved. ⚠ TO CONFIRM contractual notification window (commonly 72 hours).
6. **Remediate, then write it up** (§17.5).

### 17.4 Production issue escalation

```
Developer on duty
   │ cannot resolve within 30 min, or severity is S1/S2
   ▼
Deepak / Saranjeet  (application + database + S3)
   │ infrastructure, cost or client-facing decision
   ▼
Gaurav  (production owner)
   │ client-facing communication
   ▼
Client
```

### 17.5 Root cause analysis

Every S1, and every S2 that recurs, gets a written RCA within five working days covering: timeline, impact, root cause (not the symptom), why existing controls did not catch it, and the specific preventive change — with an owner and a date.

### 17.6 Hotfix process

1. Branch from `main` (not from the in-progress feature branch).
2. The smallest change that fixes the issue — no refactoring rides along on a hotfix.
3. Expedited review: still reviewed, never self-merged.
4. Deploy, verify in production, then merge back so the fix is not lost in the next release.
5. Record it in the release notes.

| Stage | Rule |
|---|---|
| **New feature approval** | Requested by the client or product owner, scoped and estimated by engineering, approved before work starts. Scope changes mid-build are agreed explicitly, not absorbed silently. |

## 21. Known Gaps & Remediation Plan

Stating these openly is what makes the rest of the document credible. Nothing here is a live exploit; each is a hardening item with a clear fix.

| # | Gap | Risk | Recommended fix | Priority |
|---|---|---|---|---|
| 1 | **API tokens never expire** (`sanctum.expiration = null`) | A leaked bearer token is valid forever | Set `SANCTUM_TOKEN_EXPIRATION` (e.g. 1440 minutes) and add token refresh in the clients | **High** |
| 2 | **No `.env.example` in the repository** | A new environment can be stood up with a missing or wrong key, silently | Commit a fully keyed `.env.example` with empty values covering every `env()` call in `config/` | **High** |
| 3 | **`SESSION_SECURE_COOKIE` is environment-driven with no default** | If unset in production, session cookies can travel over plain HTTP | Set it to `true` explicitly in the production environment and document it | **High** |
| 4 | **No error-monitoring service** | Production exceptions are only visible by reading log files on the server | Wire in Sentry or Bugsnag; keep the Slack critical channel as a secondary alert | **High** |
| 5 | **Test coverage is narrow** | Four feature tests, all carrier-portal. Broker RBAC, onboarding and scoring are untested. | Add feature tests for the permission matrix, the onboarding wizard state machine and tenant scoping | **High** |
| 6 | **`SESSION_ENCRYPT` defaults to `false`** | Session payloads sit unencrypted in the database | Enable, or confirm no sensitive data is placed in the session | Medium |
| 7 | **Secrets live in `.env` on the instance** | Anyone with server access can read every third-party credential | Migrate to AWS Secrets Manager or SSM Parameter Store | Medium |
| 8 | **`CarrierConnectController` is very large** (~1,800 lines) | Concentration of complexity in the most security-sensitive flow makes review harder | Extract the wizard steps into services, matching the pattern used everywhere else in the codebase | Medium |
| 9 | **DT Pay defined in policy but not exposed** | The permission matrix promises payment capability the API does not yet serve | Either implement the DT Pay API surface or mark the permissions as reserved so the UI does not offer them | Medium |
| 10 | **Legacy `DtPay` / `Models\Carriers` code is unrouted** | Dead code is a maintenance and audit liability | Remove it or move it behind a clearly labelled legacy namespace | Low |
| 11 | **No dependency vulnerability scanning in CI** | A known CVE in a dependency could ship unnoticed | Add `composer audit` to the CI pipeline and enable Dependabot | Medium |
| 12 | **Backup restores are not verifiably tested** | An unrestorable backup is discovered only during a real incident | Quarterly restore drill into a scratch environment, with the result recorded | **High** |
| 13 | **`storage/framework/sessions` artefacts tracked in git** | Repository noise; a risk of committing real session data | Add to `.gitignore` and remove from the index | Low |
